Nexo, step by step

This walkthrough builds a knowledge graph from two short documents and answers a question that neither document answers alone. Each step calls the same code Nexo runs in production, one piece at a time, so you can see what every stage adds.

The documents are fictional. One is an investor note saying Acme Holdings (also written "AHI") bought Beta Labs. The other is a clinic's supplier review saying Gamma Clinics buys test kits from Beta Labs. The question: how is Acme Holdings connected to Gamma Clinics?

Run it yourself: set up the stack as in Run it: make env PRESET=mac-single, make up, then make check, which should report every model role ok. Then make install-notebook and make notebook open walkthrough.ipynb in Jupyter, or run python examples/walkthrough.py. The outputs below come from a real run of that notebook on an Apple M5 Pro with the m5-pro-24 profile, Ollama and Neo4j. Models are not deterministic, so your wording will differ.

Setup

Settings reads the files make env and make up wrote, so the hardware profile picks the models. Generated passwords are not in those files: Nexo reads them from your private config file (~/.config/nexo/config) and keeps them out of the environment. Three overrides keep this run separate from your own data: its own chunk store file, an in-memory checkpointer, and the example relation vocabulary. Message capture in traces is off by default; it is turned on here so a later step can show the exact queries the agent wrote. This cell also imports everything the later steps use.

1. Split documents along their structure

Retrieval works on chunks, and a chunk is only useful if it holds one coherent idea. Nexo splits on Markdown headings first and only then by size, and keeps the heading path with each chunk. Chunk ids are derived from the content, so re-ingesting an unchanged document is a no-op.

2. Classify each chunk's sensitivity

Every chunk gets a level: public, internal, PII or PHI. Callers only see chunks at or below their clearance, and later every node and edge in the graph inherits a level from the chunks that support it. Here a regular-expression detector finds the email address in the Leadership section.

detector = RegexDetector()
levels = []
for chunk in chunks:
    found = detector.detect(chunk.text)
    levels.append(
        {
            "section": chunk.section_path[-1],
            "detected": [d.category for d in found],
            "sensitivity": classify(found, chunk.sensitivity).value,
        }
    )
show(levels)

3. Extract facts with a schema

The extraction model reads one chunk at a time and must answer in a JSON schema: a list of (head entity, relation, tail entity) facts, each with a verbatim quote as evidence. The server constrains the output to the schema. Nexo then drops any fact whose quote does not appear in the chunk, which is the first guard against invented facts.

ontology = Ontology.load(settings.ontology_path)
extractor = KnowledgeGraphIngestor(
    llm=build_chat_model(settings, role="extraction"),
    detector=detector,
    settings=settings,
    targets=IngestionTargets(chunk_store=None, graph_writer=None),  # extract only
    aids=ExtractionAids(ontology=ontology),
)

4. Map relations onto a vocabulary

Models phrase the same fact many ways: "bought", "acquired", "was acquired by". A relation vocabulary maps synonyms onto one canonical relation, flips inverses so direction is consistent, and checks the entity types. Anything it does not know is kept as RELATED_TO with the original predicate, rather than lost.

ORG = EntityType.ORGANIZATION
for predicate in ["BOUGHT", "ACQUIRED_BY", "BUYS_FROM", "SPONSORS"]:
    mapping = ontology.map(predicate, ORG, ORG)
    show(f"{predicate:<12} -> {mapping.relation:<10} reversed: {mapping.swap}")
Output
BOUGHT       -> ACQUIRED   reversed: False
ACQUIRED_BY  -> ACQUIRED   reversed: True
BUYS_FROM    -> SUPPLIES   reversed: True
SPONSORS     -> RELATED_TO reversed: False

5. Resolve names to one entity

"Acme Holdings Inc.", "AHI" and, in the other document, "Acme" are one company. Resolution happens in layers: a normalized key removes legal suffixes and articles; aliases stated in the text merge into the most complete name; and when a document is written to the graph, a model compares new names with existing entities of the same type only. Every merge is recorded so it can be undone.

show(
    {
        name: normalize_name(name, ORG)
        for name in ["Acme Holdings Inc.", "The Acme Holdings, Inc.", "AHI"]
    }
)

mentions = [
    EntityRef(name="Acme Holdings Inc.", type=ORG, aliases=["AHI"]),
    EntityRef(name="AHI", type=ORG),
    EntityRef(name="Beta Labs", type=ORG),
]
resolved = EntityResolver(catalog=None, llm=None, mode="deterministic").resolve(
    mentions
)
show({key: f"{r.method.value} -> {r.key}" for key, r in resolved.items()})

7. Look at the graph

Every relation keeps the chunk it came from, so any answer can be traced back to its source. Note where "Acme" from the clinic's review ended up, and that each entity carries the sensitivity of the least sensitive chunk that supports it: Jane Roe appears only in the PII chunk.

Look closely and you may also find mistakes. A 9-billion-parameter model sometimes reverses a relation or picks one its quote does not support. Nexo does not hide that: every edge points at its chunk, the agent reads that text before answering, and a person reviews the answer.

8. Search: keywords, meaning, or both

The agent can start from a search over chunks. Keyword search (BM25) finds exact names and codes; vector search finds paraphrases; hybrid search combines both rankings with Reciprocal Rank Fusion. The query below paraphrases "buys its respiratory test kits from Beta Labs"; compare the three rankings.

QUERY = "Which company provides diagnostics to the clinic?"
for mode in ("keyword", "vector", "hybrid"):
    store = LocalChunkStore(
        build_embeddings(settings), settings.vector_store_path, mode=mode
    )
    hits = store.search(QUERY, k=3, chunk_filter=ChunkFilter())
    show(
        f"{mode:<8} "
        + " | ".join(f"{h.source_id} > {h.section_path[-1]}" for h in hits)
    )
Output

9. Let a model query the graph, safely

The agent writes its own Cypher, so Nexo never trusts it: queries run in a read-only transaction with a timeout and a row cap, under a read-only database user when configured. Before that, a validator rejects anything that is not a single read query.

for cypher in [
    "MATCH (o:Organization) RETURN o.name LIMIT 5",
    "MATCH (o:Organization) DETACH DELETE o",
    "CALL dbms.components()",
]:
    try:
        validate_read_only_cypher(cypher)
        show(f"allowed   {cypher}")
    except UnsafeCypherError as exc:
        show(f"rejected  {cypher}\n          {exc}")
Output
allowed   MATCH (o:Organization) RETURN o.name LIMIT 5
rejected  MATCH (o:Organization) DETACH DELETE o
          read-only access: DETACH is not allowed
rejected  CALL dbms.components()
          procedure calls are not allowed (subqueries and db.labels() etc. are)

10. Investigate with an agent

The investigator is a Strands agent with two tools: query_knowledge_graph (read-only Cypher) and fetch_vector_chunks (the exact text behind a chunk id). It decides what to follow. It may only cite chunks it actually fetched, and it stops at a turn and token budget.

chunk_store = LocalChunkStore(build_embeddings(settings), settings.vector_store_path)
investigator = Investigator(
    model=build_strands_model(settings),
    graph=graph,
    chunks=chunk_store,
    settings=settings,
    schema_text=graph.describe_schema(),
)
spans.clear()
output = investigator.investigate("How is Acme Holdings connected to Gamma Clinics?")
show(output.answer)
show(
    {
        "citations": output.citations,
        "tool_calls": [f"{c.tool}: {c.detail}" for c in output.tool_calls],
        "stop_reason": output.stop_reason,
    }
)

11. Put it in a workflow with human review

The agent is one step of a fixed LangGraph workflow. A router checks the request first. The investigator runs inside a retried task. Compliance checks the draft (uncited claims, citations to text the agent never read, sensitive data) and then pauses the run until a person decides. The pause is checkpointed, so the decision can come from another process, days later.

12. Clearance decides what the agent can see

The Leadership chunk holds an email address, so it is PII. A caller with the default internal clearance cannot see that chunk, and the agent cannot use it: it should report what it could not find rather than guess. With pii clearance, the same question gets a different answer.

If the internal answer still names the person, that name came from a graph query that returned a plain value (p.name) rather than a whole node. Nexo redacts nodes above the caller's clearance, but on Neo4j Community it cannot tell where a plain value came from. Neo4j Enterprise closes this gap with role-based access on the :PII and :PHI labels; on Community, withheld chunks and human review are the remaining controls (ADR-0006 in the decision records).

13. Use the graph from other clients over MCP

nexo mcp exposes the same graph to Claude Code or any MCP client as read-only tools, with the same clearance and Cypher safeguards. Here the server runs in-process.

server = build_mcp_server(graph=graph, chunks=chunk_store, settings=settings)


async def find_entity(name):
    """List the server's tools and call nexo_find_entities for one name."""
    async with Client(server) as client:
        tools = await client.list_tools()
        response = await client.call_tool("nexo_find_entities", {"name": name})
        return [t.name for t in tools.tools], response.structured_content

    """Indented span names of a trace subtree, children in start order."""
